# 要件定義 — stripe-freee-bridge

## 1. 概要

**Stripeで受けた売上を、freee会計の仕訳へ計上するための連携。**

Stripeの入金は**手数料が差し引かれた金額**で銀行口座へ届く。そのため通帳の数字だけを見て記帳すると、
売上が手数料のぶん小さく計上される。これを正しく「売上総額」と「支払手数料」に分け、
さらに入金があった時点で未収入金を消し込むところまでを自動化する。

## 2. なぜ作るか

受託開発で使えるモダン技術スタックの実績づくり（技術スタック速習カリキュラムの一環）。
**Findyのスキル偏差値対策ではない。**

題材にStripe×会計APIを選んだ理由は、経理・財務20年の実務知識が最も濃く出る領域だから。
「手数料差引後の入金を、売上総額と手数料に分けて計上する」「payout単位で未収入金を消し込む」は、
実務を知らないと設計できない。

## 3. スコープ

### 3.1 やること

| 段階 | 内容 |
| --- | --- |
| **P1** | Stripe Webhookの受け口・署名検証・冪等性・**仕訳案の組み立て**（freeeへは投げない） |
| **P2** | freee APIへの投入（トークン更新の直列化を含む）。**テスト用事業所**が相手 |
| **P3** | 入金消込（payout）、返金の取り扱い |

### 3.2 やらないこと

- **実帳簿（本番の事業所） へは書き込まない**（2026-09-08 オーナー指示）。
  相手は freee の**テスト用事業所**に限る
- `freee-setup` リポジトリには手を入れない（移行完了済みで「原則さわらない」方針）。
  技術的な知見だけを持ってくる
- Stripeの本番決済は扱わない。**Test モード**で完結させる（課金ゼロ）

## 4. 設計の中心となる考え方

### 4.1 AIは仕訳案を出すだけ。freeeへの投入は人が承認してから

`keiri-ai` の「**AIに確定権限を持たせない**」、`freee-setup` の
「**1期入れたら必ず検算してから次へ進む**」と同じ形にする。

```
Stripeイベント → 仕訳案をD1に貯める → 人が画面で確認 → freeeへ投入
```

Webhookを受けた瞬間にfreeeへ投げる作りにしない。理由は2つ。

1. **freeeには一括削除APIが無い**（`freee-setup` が全96エンドポイントを走査して確認済み）。
   間違えて投入すると1件ずつ消すことになる
2. 会計は「入った」と「合っている」が別のこと。取り込みエラーが0件でも、
   科目の当て方を1つ間違えれば決算書は静かにずれる

### 4.2 仕訳の形

Stripeで1,000円の商品が売れ、手数料が36円だった場合。

**売上計上時**（`charge.succeeded`）

| | 借方 | | 貸方 | |
| --- | --- | --- | --- | --- |
| | 未収入金（Stripe） | 964 | 売上高 | 1,000 |
| | 支払手数料 | 36 | | |

**入金時**（`payout.paid`）— 複数の売上がまとまって銀行へ届く

| | 借方 | | 貸方 | |
| --- | --- | --- | --- | --- |
| | 普通預金 | 964 | 未収入金（Stripe） | 964 |

**返金時**（`charge.refunded`）— Stripeは返金しても決済手数料を返さないため、支払手数料は戻さない

| | 借方 | | 貸方 | |
| --- | --- | --- | --- | --- |
| | 売上高 | 1,000 | 未収入金（Stripe） | 1,000 |

### 4.3 税区分

`freee-setup` で確定した事業者の実態は**免税事業者・インボイス登録なし**のため、
実帳簿では税区分「対象外」で統一している。
**ただしテスト用事業所の設定は別途確認する**（未確認のまま実装しない）。

税区分は設定値として外に出し、コードへ直書きしない。

## 5. 機能要件

| ID | 要件 |
| --- | --- |
| F-1 | Stripe Webhookを受け、**署名を検証**する。検証に失敗したリクエストは処理しない |
| F-2 | 署名検証はタイムスタンプの許容差を持ち、**リプレイ攻撃**を弾く |
| F-3 | 同じイベントを複数回受け取っても**二重計上しない**（Stripeはat-least-once配信） |
| F-4 | 受け取ったイベントから仕訳案を組み立て、D1へ保存する |
| F-5 | 仕訳案は**貸借が一致していなければ保存しない** |
| F-6 | 仕訳案を人が確認できる画面を持つ |
| F-7 | freeeへ投入したら、**投入したIDを全件記録する**（記録が無いと取り消せない） |
| F-8 | freeeのアクセストークン更新は**同時に2つ走らせない** |

## 6. 非機能要件

| ID | 要件 |
| --- | --- |
| NF-1 | Cloudflare Workers + D1 で動く。無料枠内 |
| NF-2 | 秘密情報（Stripe webhook secret、freeeのトークン）は**コードにもコミットにも残さない**。Workers Secretsに置く |
| NF-3 | ログに秘密情報・個人情報を出さない。**Stripeの顧客名やメールアドレスは保存しない** |
| NF-4 | 公開リポジトリにする前提で作る。実在の事業所ID・口座番号を含めない |

## 7. 既知の制約（`freee-setup` の実測から引き継ぐ）

| 制約 | 出典 |
| --- | --- |
| freeeのアクセストークンは**6時間で失効**する | 2026-08-29 実測（401 `expired_access_token`） |
| リフレッシュトークンは**1回使うと入れ替わり、古いほうはその場で死ぬ**。保存し損ねるとブラウザ認可からやり直し | 2026-08-29 実測 |
| **一括インポートAPIも一括削除APIも無い。**投入も削除も1件ずつ | 全96エンドポイントを機械走査して確認 |
| freeeの事業年度はAPIで作れない（画面で年度締め） | 2026-08-29 実測 |
| 投入直後の試算表は**反映が遅れる**（取り直すと一致） | 移行時に毎期2〜4件ずれた |

**トークン更新がWorkersで問題になる理由:** リフレッシュトークンが使い捨てなので、
2つのリクエストが同時に更新すると片方が死ぬ。Workersは並行実行されるため、
**D1の条件付きUPDATEで排他ロックを取ってから更新する**（F-8）。

## 8. 確認が必要だった事項 — **2026-09-08 にすべて実測で解決**

| ID | 内容 | 実測結果 |
| --- | --- | --- |
| U-1 | テスト用事業所の company_id | **12785959**（開発用テスト事業所）。実帳簿「ラク屋」（実帳簿ID） とは別 |
| U-2 | 税区分の設定（課税か免税か） | **免税。**税区分「対象外」(code 2) が `available: true` |
| U-3 | 必要な勘定科目の有無 | 未収入金 `1072165672` ／ 支払手数料 `1072165784` ／ 売上高 `1072165747` は**存在**。**`普通預金` は無い**（P3で作成が要る） |
| U-4 | StripeアカウントのTestモード | **あり**（オーナー確認） |

**U-2の確かめ方:** `fiscal_years[].tax_method` の値が何を意味するかはAPIドキュメントを読んでいないため、
**免税と確定済みの実帳簿（ラク屋）と突き合わせた。**両方とも `tax_method=0` で一致したので、
テスト事業所も同じ扱いと判断している。ラク屋が免税・インボイス登録なしであることは
`freee-setup` で2026-08-25にオーナーが確認した事実。

事業年度は両事業所とも **2026-01-01〜2026-12-31・未締め**。

## 9. freeeアプリ登録を分ける（2026-09-08 オーナー承認）

**`freee-setup` とは別のfreeeアプリ（別の client_id / client_secret）を使う。**

**Why:** freeeのリフレッシュトークンは**1回使うと入れ替わり、古いほうはその場で死ぬ。**
同じアプリ登録を2つのプロジェクトで共有すると、**片方が更新した瞬間にもう片方が死ぬ。**
2026-09-08に実際にfreee-setup側のトークンが失効してブラウザ再認可からやり直しになっており、
同じ形の事故を構造として作り込まないための分離。

**あわせて守ること:** `freee-setup/.env` の `FREEE_COMPANY_ID`（実帳簿を指している）は**変更しない。**
`freee_write.py` / `post_journals.py` は allowlist を持たず、この値をそのまま書き込み先にするため、
書き換えるとfreee-setup側の検算経路が静かにずれる。

## 10. トークンの持ち方（P2の設計）

Workersは実行中にSecretsを書き換えられないが、freeeのリフレッシュトークンは**使うたびに変わる。**
そのためトークンはD1に持つ。

**同時更新の防ぎ方（F-8）:** Workersは並行実行されるので、2つのリクエストが同時に更新すると
片方が死ぬ。D1の**条件付きUPDATEでリースを取ってから**更新する。

```sql
UPDATE freee_tokens SET refreshing_until = ?
 WHERE id = 1 AND (refreshing_until IS NULL OR refreshing_until < ?)
```

`changes = 1` を得た実行だけが更新する。リースには期限を持たせ、
更新中に落ちても永久ロックにならないようにする。
