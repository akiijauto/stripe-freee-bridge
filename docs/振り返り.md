## 2026-09-08 — P1（Webhookの受け口〜仕訳案の組み立て）

### やったこと

### 計上日がUTCになっていた — 実際に動かして初めて見つかった

試験は全部通り、型検査も通っていた。**それでも間違っていた。**

ローカルで実際に署名付きのリクエストを投げ、確認画面を見たら `issue_date` が
**`2026-09-07`** になっていた。そのときの日本時間は 9/8 の朝7時である。

原因は `new Date(seconds * 1000).toISOString()` で日付を切っていたこと。
これはUTCの日付なので、**日本時間の朝9時前の取引がすべて前日付になる。**

| いつの取引か | UTCで切る | JSTで切る |
| --- | --- | --- |
| 2026-09-08 07:00 JST | 2026-09-07 | 2026-09-08 |
| 2026-12-31 23:00 JST | 2026-12-31 | 2026-12-31 |
| **2027-01-01 08:00 JST** | **2026-12-31** | **2027-01-01** |

**いちばん下が危ない。**元日の朝の売上が、前の事業年度へ落ちる。
決算を締めたあとに1件増えることになり、確定申告の数字が変わる。

`+9時間してから切る`ように直し、上の3件を試験に足した。

### 気付けた理由と、気付けなかった理由

**気付けたのは、応答（JSON）ではなく画面を見たからではない。**
実際に**動かして値を見た**からである。試験では自分で作った固定のUNIX秒を使っており、
その期待値も自分で決めていたので、**UTCで切る前提のまま辻褄が合っていた。**

`feedback_verify_on_screen`（サーバーの応答と利用者の画面は別）と
`feedback_completion_criteria`（緑は「壊れていない」証明であって「出来ている」証明ではない）が、
そのまま出た形になる。**試験が全部緑でも、実際の時刻で動かすまで分からない種類の誤りがあった。**

### 推測で0円を入れない、という判断

Stripeの手数料は `charge` の `balance_transaction` を展開しないと取れない。
Webhookのpayloadでは文字列IDのままのことがある。

ここで**取れなかったときに0円で通す作りにしなかった。**0円で通すと、
手数料が費用に立たず、売上だけが総額で計上される。**貸借は合うので検算をすり抜ける。**
金額が合っている以上、誰も気づけない。

そのため「展開されていない」ときは仕訳にせず、`failed_events` へ理由つきで残すことにした。
**仕訳にできなかったものを黙って捨てると、売上が1件抜けたことに誰も気づけない**ためでもある。

これは `freee-setup` で踏んだ「税区分だけずれると金額は合うので検算をすり抜ける」と同じ形である。

### 円以外の通貨を拒んだ

Stripeの `amount` は通貨の最小単位で来る。円は最小単位が1円なのでそのまま使えるが、
ドルはセントなので**同じ扱いにすると100倍ずれる。**
対応通貨を明示的に円だけに絞り、それ以外は例外にした。

### 引き継いだ制約（`freee-setup` の実測から）

自分で確かめ直していないが、同じオーナーの案件で実測済みのものを前提に設計した。

- freeeのアクセストークンは6時間で失効する
- **リフレッシュトークンは1回使うと入れ替わり、古いほうはその場で死ぬ**
- 一括インポートAPIも一括削除APIも無い（全96エンドポイントを走査して確認済み）

3つ目があるので、**投入は人が承認してから**という形にした。
2つ目はP2で効いてくる。Workersは並行実行されるので、2つのリクエストが同時に
トークンを更新すると片方が死ぬ。**D1の条件付きUPDATEで排他ロックを取ってから更新する**設計にする。

運用中に何度も通る道になる。使い捨てのスクリプトにしておく道理がない。

## 2026-09-08（続き）— P3と本番デプロイ。**摘要が抜けていたのはオーナーが見つけた**

### 摘要をfreeeへ送っていなかった

P2の投入は「貸借一致・税区分・発生日・会社ID」を全部確かめて通したつもりだったが、

`memo`（`Stripe売上 ch_xxx`）は**D1には保存していたが、freeeへ送っていなかった。**
`details[].description` に載せていなかったので、freeeの画面には摘要が空の伝票が並ぶ。

**これが痛いのは、突き合わせる手がかりが帳簿側に残らないこと。**
金額も貸借も税区分も正しいので、**検算をすり抜ける。**
「手数料が取れないときに0円を入れない」と同じ形の誤りを、別の場所でやっていた。

**自分の検算項目に「摘要」が入っていなかったから気付けなかった。**
数字が合うことばかり見て、**帳簿として後から追えるかを見ていなかった。**
会計の正しさは貸借一致だけではない、という当たり前をひとつ落としていた。

直したうえで、**全明細に摘要が載ることを試験に足した**（fetchを差し替えて送信本文を検査する）。

既定の `Python-urllib/3.x` が弾かれていた。Discord Webhook で同じことを踏んで
記録してあったのに、**別のサービスで同じ形を繰り返した。**

**「403 が返った」と「アプリが壊れている」は別である。**
確かめる道具のほうが弾かれていることがある。

## 2026-09-08（続き）— 本物のStripeイベントで落ちた。そして照合を足した

### 本物のWebhookは、こちらの想定と違う形で来た

Stripeダッシュボードにエンドポイントを登録し、**本物のテスト決済**（4,500円）を流したら、
仕訳案ができなかった。`failed_events` を見ると理由が残っていた。

```
balance_transaction is not expanded; fee is unknown (do not assume zero)
```

**設計どおり止まっていた。**0円で通していれば手数料178円が費用に立たず、
貸借は合うまま静かにずれていた。**止める側に倒しておいたのが効いた。**

ただし、止まったままでは仕組みとして使えない。原因を実測した。

| 見たもの | 実測 |
| --- | --- |
| イベント内の `balance_transaction` | **null** |
| いまAPIで取り直した charge の `balance_transaction` | `txn_3UDGTjBpvSRtLjGc1mtr1U10` |

**決済の成立と残高取引の作成にタイムラグがある。**
`charge.succeeded` が飛ぶ時点では、手数料はまだ確定していない。

最初は「文字列IDで届くはず」と考えて balance_transaction を取りに行く実装にしたが、
**実物は null だった。**そこで charge 自体を `expand[]=balance_transaction` で取り直す形に変えた。
それでも未確定なら 500 を返し、Stripeに再送させる（黙って捨てない）。

**「文字列IDで届く」は私の想像で、実測ではなかった。**
実物を1回流すまで、間違った前提のまま実装していた。

### 3DSで決済APIが使えなかった

試験用の決済を作ろうとして Charges API を叩いたら 402 で落ちた。

```
Your charge was declined due to the Japan 3DS mandate.
You should migrate to the Payment Intents API
```

日本の3DS義務化で、旧APIでは決済を作れない。Payment Intents API へ切り替えて通った。
**日本特有の制約は、日本で試すまで出てこない。**

### 本番の403は、こちらの投げ方の問題だった（再掲・2回目）

本番URLへ Python の `urllib` でアクセスして 403。User-Agent を付けたら 200。
**Discord Webhook で同じことを踏んで記録してあったのに、また踏んだ。**
記録は「読める場所にある」だけでは効かない。

### 照合を足した（オーナー提案）

オーナーから **「月次の棚卸照合。Stripeと会計で本当に一致した金額がもれなく連動されたかを
定期チェックする。チェックが漏ればユーザーへ注意を通知する」** という提案があった。

これは今回の件がそのまま裏づけになっている。
**仕組みが「止まった」ことには気付けても、「1件だけ抜けた」ことには気付けない。**
今回は私が画面を見に行ったから気付いたが、Stripeの再送には回数の限りがあり、
諦められた時点で売上が抜けたまま誰も気付かなくなる。

毎日 JST 07:00 の Cron で突き合わせ、**差があるときだけ**Discordへ通知する形にした。

**承認待ちが残っているうちは金額差では鳴らさない。**
未投入ぶんは差が出て当然で、そこで鳴らすと**鳴りっぱなしになり、見張りが無視されるようになる。**
`automation-lab` の `#errors` を「静かなのが正常」に設計したのと同じ考え方。

実データで走らせたら、正しく鳴った。

```
Stripe 売上 5,480円 / 手数料 217円
freee  売上 13,000円 / 手数料 1,188円
[error] 仕訳にできなかったイベント: 1件
[warn]  未投入の仕訳案: 1件
```

**差が出るのが正しい状態だった。**freee側が多いのは、手動テストで投入した架空の仕訳
（PRODTEST 3,000円、P3テスト 20,000円と返金▲20,000円）が入っているため。

### Cronが登録されていなかった。**設定ファイルを2つに分けた副作用**

デプロイしたのに Cloudflare の schedules API が `{"schedules": []}` を返した。

原因は、**`wrangler.local.jsonc` が Cron 追加より前に複製したものだった**こと。
公開用の `wrangler.jsonc` にだけ `triggers` を足しており、
実際にデプロイに使う `wrangler.local.jsonc` は古いままだった。

**設定ファイルを2つに分けると、片方だけ直す事故が起きる。**
秘密を公開リポジトリへ入れないための分離だが、代償としてこの穴ができた。
複製し直して解決したが、**次に設定を変えるときも同じ穴を踏みうる。**

気付けたのは、`cf-vps-monitor` で「Cron は API 応答だけを信用せず実測する」と
記録していたから。**同じ形の失敗を、記録のおかげで2回目は自分で見つけられた。**
